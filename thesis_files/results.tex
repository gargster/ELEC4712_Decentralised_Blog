\section{Results}\label{sec:results}
This section evaluates the implemented prototype through end-to-end demonstrations and focused security checks. The walkthrough follows the order in which the system was exercised rather than treating every command as an isolated feature: Alice creates and publishes an identity, creates social actions, discovers and follows Bob, replicates and interacts with his post, and publishes her feed. A second workflow demonstrates multi-hop propagation through Bob from Charlie to Alice. The final scenarios test rejection of tampered actions, an impersonation attempt, and a replacement profile that conflicts with the directory. These results provide implementation-level evidence for the architecture in Section~\ref{sec:system-design} and the client behaviour described in Section~\ref{sec:implementation}.

\subsection{Identity Creation and Publication}
Before creating an identity, the client can be started from the \texttt{client} directory with \texttt{python app.py}; this displays the available commands and examples. New users initialise their repository from the canonical template, which provides the standard repository layout used by the protocol. Alice's identity was created with:

\begin{lstlisting}
python app.py profile create --handle alice.social --name Alice --bio "Software Engineering student at USYD"
\end{lstlisting}

The command cloned the canonical repository, generated an Ed25519 key pair, and created a signed \texttt{social/profile.json}. At this point, \texttt{repoURL} was \texttt{null}, because Alice's local repository had not yet been published. Figure~\ref{fig:results-clone-canonical} shows the repository initialised from the canonical template. The initial profile therefore contains Alice's cryptographic identity before it has a published repository location.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/clone_canonical.png}
    \caption{Alice's local repository initialised from the canonical template}
    \label{fig:results-clone-canonical}
\end{figure}

Before publication, an empty remote repository was created on the Git hosting platform. Alice then published her local repository using:

\begin{lstlisting}
python app.py publish --url https://github.com/gargster/alices-social.git
\end{lstlisting}

The command pushed the repository, updated \texttt{repoURL}, re-signed the profile, and registered Alice in the social directory. Figure~\ref{fig:results-publish-user} shows the resulting repository and protocol files. The public key remains the same across publication; the repository URL is added as the hosting location. This illustrates the separation between the cryptographic identity and its current repository location described in Section~\ref{sec:system-design}.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/publish_alice_repo.png}
    \caption{Alice's published repository containing the protocol files}
    \label{fig:results-publish-user}
\end{figure}

Publishing also updated \texttt{directory.json} in the social-directory repository. Figure~\ref{fig:results-directory-entry} shows Alice's directory entry. Alice can then access the statically hosted social-directory website at \url{https://gargster.github.io/social-directory/}. Figure~\ref{fig:results-directory-site} shows Alice's account on the public directory website.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/directory_with_alice.png}
    \caption{Alice's handle, repository URL and public key registered in the social directory}
    \label{fig:results-directory-entry}
\end{figure}

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/directory_web_alice.png}
    \caption{Social-directory website displaying Alice's account}
    \label{fig:results-directory-site}
\end{figure}

Together, these results demonstrate identity creation and publication. The signed profile is stored with the user's protocol data, while the directory provides a public mapping from handle to repository URL and public key. The directory is a trusted source for this mapping: a valid profile signature alone does not establish ownership of a human-readable handle.

Figure~\ref{fig:results-replicated-bob-post} shows the replicated copy of Bob's post stored in Alice's repository. \subsection{Multi-Hop Replication: Charlie to Bob to Alice}
A second workflow tested whether Alice could receive an action from someone she did not directly follow. Charlie created an identity and published his repository:

\begin{lstlisting}
python app.py profile create --handle charlie.social --name Charlie --bio "Civil Engineering Student at UNSW"
python app.py publish --url https://github.com/gargster/charlie-social.git
\end{lstlisting}

Charlie then created a post:

\begin{lstlisting}
python app.py post "Hi, my name is Charlie I am studying Civil Engineering at UNSW"
\end{lstlisting}

Figure~\ref{fig:results-charlie-post} shows Charlie's post in his repository. Bob followed Charlie and replicated from his configured remotes:

\begin{lstlisting}
python app.py follow charlie.social https://github.com/gargster/charlie-social.git
python app.py replicate
\end{lstlisting}

Charlie's post was accepted into Bob's local action store, as shown in Figure~\ref{fig:results-bob-charlie}. Alice then ran \texttt{python app.py replicate} again. The same Charlie action appeared in Alice's repository, as shown in Figure~\ref{fig:results-alice-charlie}. Alice therefore received the post through Bob, even though Charlie was not a direct follow in this tested path.

\subsubsection{Repository Replacement}

The third test examined whether a different public key could replace the identity registered for \texttt{case3-target.social} while retaining the same handle and repository URL. Figure~\ref{fig:results-directory-original-key} shows the original entry in \texttt{social-directory/directory.json}, including the public key registered for this handle (beginning \texttt{040e242f}).

I then used the project's \texttt{KeyPair}, \texttt{Signer}, and \texttt{ProfileVerifier} classes to generate a replacement profile for the same handle. The new profile was signed using the newly generated key. The verification output reported that the replacement profile was internally valid, but its public key began \texttt{058f010c}, rather than the registered key's prefix \texttt{040e242f}. Figure~\ref{fig:results-replacement-profile} shows the resulting \texttt{profile.json}, where the replacement key can be compared with the original directory entry. Thus, the profile's signature was valid, but the public key differed from the one already registered for the handle.

After committing and pushing the replacement profile to the test repository, I attempted to follow the account from Alice's client:

\begin{samepage}
\Needspace{5\baselineskip}
\begin{lstlisting}[breaklines=true]
python app.py follow case3-target.social
\end{lstlisting}
\end{samepage}

The follow operation was rejected, as shown in Figure~\ref{fig:results-reject-replacement}, and no Follow action was created in Alice's repository. The client therefore did not accept a profile just because it was internally valid: its public key also had to match the key registered for that handle in the social directory. This protection relies on trusting the directory's handle-to-key mapping.

\subsection{Results Summary}
The end-to-end workflow demonstrates that the prototype can create and publish signed identities, store signed social actions, discover and follow accounts through a public directory, replicate and validate remote actions, support Like and Reply interactions, propagate a post across multiple repositories, and publish the resulting local feed as a static website. The security tests show rejection of the tested tampered action, impersonation attempt and replacement profile. These results provide practical evidence for the design in Section~\ref{sec:system-design} and the implementation in Section~\ref{sec:implementation}. The scope and limitations of these results, including the directory trust assumption and the prototype's deployment model, are discussed in the Discussion section.
