\subsection{Prototype Overview}
The prototype is built using the following tools and technologies:
\begin{itemize}
    \item Git for version control and repository-based storage and exchange;
    \item Python for the client-side protocol operations;
    \item HTML, CSS and JavaScript for the feed and directory websites;
    \item GitHub for hosting user and directory repositories, with
    GitHub Pages serving the static websites; and
    \item PyNaCl and GitPython for cryptographic and Git operations
    in the Python client.
\end{itemize}

The repository contains the \texttt{client} source code with a dedicated \texttt{tests} directory containing the automated test suite. Documentation including \texttt{README.md}, which explains how to run the prototype, and \texttt{latest\_design.md}, which contains the latest design documentation and workflow diagrams are also in the repository. Earlier design iterations are retained in the \texttt{docs/archive} directory. 

The client entry point is \texttt{client/app.py}. Running \texttt{python app.py} from the \texttt{client} directory displays the available commands, including identity creation, social actions, following, replication, feed display and site publication. Automated testing is implemented using \texttt{pytest}; the testing methodology and results are presented in Chapter~6.

Figure~\ref{fig:implementation_architecture} summarises the organisation of the prototype implementation. User commands are dispatched to the Identity, Actions, Replication, Publishing, and Following \& Discovery modules. The classes within these modules implement the functionality required to realise the protocol design presented in Chapter~4. The implementation also interacts with two external Git repositories: \texttt{canonical-social}, which provides the repository and website templates, and \texttt{social-directory}, which provides account discovery and handle registration services.

\subsection{Identity and Signed Data}

The Identity Management component is primarily exercised through the following commands: 
\begin{itemize} 
    \item \texttt{profile create <handle> <display-name> <bio>} 
    \item \texttt{publish <repository-url>} 
\end{itemize}
The \texttt{profile create} command is handled by
\texttt{ProfileCreator}, which clones the canonical repository template and
generates an Ed25519 key pair using PyNaCl. It creates a profile containing
the user's handle, public key and profile information, then signs and saves
it as \texttt{social/profile.json}. The private key is stored separately in
the client's identity state, while the public key and signature are included
in the profile. The user then runs \texttt{publish} with the URL of the Git
repository where the identity will be hosted. \texttt{PublishManager}
publishes the repository, adds the repository URL to the profile, re-signs
and pushes the updated profile, and registers the account in the social
directory.

The \texttt{Signer} and \texttt{Verifier} classes provide the shared
JSON signing and verification operations. Before signing, \texttt{Signer}
serialises the object with sorted keys and excludes any existing signature.
It signs these bytes with the Ed25519 private key and stores the resulting
signature in Base64 form. \texttt{Verifier} decodes the signature and checks
it against the same sorted JSON representation using the public key.
\textbf{Listing~\ref{lst:signing} shows the shared byte representation used
for signing and verification.}

\begin{lstlisting}[caption={Core JSON signing and verification operations},label={lst:signing}]
message = json.dumps(obj_to_sign, sort_keys=True).encode("utf-8")
signed = self.signing_key.sign(message)
self.verify_key.verify(message, signature_bytes)
\end{lstlisting}

\texttt{ProfileVerifier} uses \texttt{Verifier} to check a profile's
signature before returning its verified handle, public key and repository
URL. Figure~\ref{fig:identity_workflow} shows the corresponding design
workflow. \textbf{The shared sorted JSON representation lets profiles and
actions use the same signing mechanism. A valid signature establishes that
the data matches the presented public key; it does not by itself link that
key to a human-readable handle. Follow makes that association by checking
the key against the public directory, which remains a trusted source for
handle registration. Signatures provide integrity and key-based authorship
verification, not confidentiality.}

\subsection{Social Action Implementation}
The Social Action component is exercised through the following commands: 
\begin{itemize} 
    \item \texttt{post <content>} 
    \item \texttt{reply <action-id> <content>} 
    \item \texttt{like <action-id>} 
    \item \texttt{follow <handle> <repository-url>} 
\end{itemize}

Social actions are stored as JSON files in the user's
\texttt{social/actions/} directory. As described in the System Design
chapter, they share common fields: an identifier, action type, author public
key, creation timestamp and signature. Since these fields and the creation
steps are common across post, reply, like and follow actions, the
implementation uses \texttt{ActionBase} to avoid duplicating this logic.

As shown in Figure~\ref{fig:action_class_diagram},
\texttt{ActionBase} defines the shared creation workflow in
\texttt{\_create()}. It loads the public key from \texttt{profile.json} and
the private key from the client's identity state, checks that the keys
correspond, generates an action ID and builds the common fields. The
ID follows the form \texttt{<type>-<handle>-<number>}, with the number
incremented from the existing local action files. It then calls
\texttt{\_extend()}, allowing each subclass to add its action-specific
fields: \texttt{PostAction} adds post content; \texttt{ReplyAction} adds
content, the \texttt{inReplyTo} action ID and target handle;
\texttt{LikeAction} adds the target action ID and target handle; and
\texttt{FollowAction} adds the followed user's public key as its target.
Finally, \texttt{ActionBase} signs and writes the JSON file. The client uses
\texttt{GitPublisher} to commit and push the created action.

This shared creation workflow uses the Template Method pattern:
\texttt{ActionBase} defines the common algorithm, while subclasses customise
the \texttt{\_extend()} step \cite{gfg_template_method}. Separately, the
prototype uses a factory design pattern to avoid duplicating the logic for
instantiating different action classes. When a user enters a command,
\texttt{ActionFactory.create(...)} obtains the corresponding class from
\texttt{ActionRegistry} and creates an instance. This allows \texttt{app.py}
to request an action by command without knowing the concrete class or its
construction details, encapsulating object creation and decoupling command
handling from action-specific implementation. The registry maps command names
to action classes, avoiding a growing chain of action-specific
\texttt{if}/\texttt{elif} branches in the factory
\cite{gfg_factory_method}.

This structure supports extension as new social actions are introduced.
To add an action, a developer can implement a class inheriting from
\texttt{ActionBase} and register it for a command; the existing factory and
its dispatch logic do not need to change. The new command must still be
connected to the CLI parser and registry, but no new action-specific branch
needs to be added to the factory. This is an example of the Open--Closed
Principle: the action system can be extended without modifying its existing
creation logic. The Post, Reply, Like and Follow sequence diagrams in the
System Design chapter
(Figures~\ref{fig:post_workflow}, \ref{fig:reply_workflow},
\ref{fig:like_workflow} and \ref{fig:follow_workflow}) show how these action
types are used in the protocol workflows.

\subsection{Following and Discovery}

The Following functionality is accessed through: 
\begin{itemize} 
    \item \texttt{follow <handle> <repository-url>} 
\end{itemize}
\textbf{The design workflow is shown in Figures~\ref{fig:discovery_workflow}
and \ref{fig:follow_workflow}. In the implementation, a Follow action
records the social relationship by targeting the other user's public key.
Separately, the repository URL is saved as a named Git remote, which gives
replication a source to fetch from. Git remote configuration therefore
avoids a second list of repository URLs, while the signed Follow action
remains the record of whom the user follows.}

Before accessing the target repository, the client retrieves the
handle's entry from the public directory and checks that the supplied
repository URL matches the registered URL. The directory response is obtained
over HTTP using \texttt{urllib.request}; the configured URL identifies the
published JSON data. The client then checks that the supplied repository URL
matches the entry's \texttt{repoURL}, rejecting a mismatch before fetching the
repository. \textbf{Listing~\ref{lst:follow-directory} shows this lookup and
URL check.}

\begin{lstlisting}[caption={Checking a Follow target against the directory},label={lst:follow-directory}]
with urllib.request.urlopen(DIRECTORY_JSON_URL, timeout=5) as response:
    directory = json.load(response)
entry = directory.get(handle)
if not isinstance(entry, dict):
    raise ValueError(f"Handle '{handle}' is not registered")
if entry.get("repoURL") != repo_url:
    raise ValueError("Repository URL does not match the directory")
\end{lstlisting}

After this check, the client adds the target repository as a named Git
remote, using the handle as the remote name. A Git remote is a saved
name-to-URL association in the local repository; it does not copy the remote
actions at this point. GitPython's \texttt{create\_remote()} adds this
configuration, which the replication process can later use to fetch the
remote branch. This reuses Git's existing remote mechanism rather than
maintaining a separate list of followed repository URLs
\cite{github_remotes}.

\textbf{A remote is added only when that handle is not already configured,
avoiding duplicate remotes.}

The client then fetches the target's \texttt{main} branch and reads
\texttt{social/profile.json} from it. \texttt{ProfileVerifier} delegates
signature checking to the shared \texttt{Verifier}; the follow operation
also compares the verified handle and public key, and the profile's repository
URL, with the requested values and the directory entry before creating the
Follow action. Thus a valid signature proves control of the profile's key,
while the directory comparison checks that this is the key registered for
the handle. \textbf{Listing~\ref{lst:follow-profile} shows these
comparisons.}

\begin{lstlisting}[caption={Validating the fetched Follow profile},label={lst:follow-profile}]
verified = ProfileVerifier(profile).verify()
if verified["handle"] != handle:
    raise ValueError("Signed profile handle does not match")
if verified["publicKey"] != registered_identity["publicKey"]:
    raise ValueError("Profile key does not match the directory")
if profile["repoURL"] != repo_url:
    raise ValueError("Profile repository URL does not match")
\end{lstlisting}

\textbf{The signature check establishes that the profile matches its key;
the comparisons bind that key and repository URL to the requested handle and
the directory entry. This helps detect a repository presenting a different
key for a registered handle, while relying on the directory's handle-to-key
mapping.}

Once the profile passes these checks, \texttt{FollowAction} creates
the signed action targeted at the verified public key. The action is
committed and pushed to the follower's repository. Fetching the remote
\texttt{main} branch to obtain the profile can also transfer Git objects from
its history, but Follow does not import the remote actions into the local
action set used by the client. The saved remote is used by the separate
replication process to discover, verify and accept actions for local use.
This keeps Follow responsible for establishing the relationship and
replication responsible for processing remote activity, as described in the
corresponding System Design workflows.

When an account is published,
\texttt{PublishManager} checks an existing entry before updating it. If the
handle already has a registered key, publication refuses to replace it with
a different key. This complements the Follow-time comparison.

\textbf{Listing~\ref{lst:registered-key} shows the publishing guard.}
\begin{lstlisting}[caption={Preventing replacement of a registered key},label={lst:registered-key}]
registered_key = entry.get("publicKey")
if registered_key != public_key:
    raise RuntimeError(
        f"Refusing to replace the registered public key for '{handle}'. "
        "Use the identity recovery process to change keys."
    )
\end{lstlisting}

The directory entry also contains an optional \texttt{siteURL}.
After site publication succeeds, \texttt{PublishManager} adds this URL to
the existing entry, allowing the directory website to link the handle to
the published feed. The repository URL remains available separately for
following and protocol access.

The directory website is a static interface to this JSON data. The social-directory repository is organised as follows: 
\begin{verbatim} 
social-directory/ 
├── directory.json # Registered handles and metadata 
├── index.html # Discovery website structure 
├── app.js # Directory loading and rendering 
└── style.css # Website styling 
\end{verbatim}

\texttt{index.html} defines elements with the IDs \texttt{member-list},
\texttt{member-count} and \texttt{directory-status}. In \texttt{app.js},
\texttt{document.querySelector()} uses these IDs to select the elements
where the directory cards, profile count and loading or empty-directory
message are displayed. The loader fetches and sorts entries from
\texttt{directory.json}, then renders a card for each handle.
\textbf{Listing~\ref{lst:directory-dom} shows the HTML elements that the
directory script selects and updates.}

\begin{lstlisting}[caption={Selecting directory cards in the DOM},label={lst:directory-dom}]
const memberList = document.querySelector("#member-list");
memberList.replaceChildren(...entries.map(
  ([handle, entry]) => renderMember(handle, entry)
));
\end{lstlisting}

\textbf{\texttt{replaceChildren()} fills the member-list element with the
cards created by \texttt{renderMember()}. The page also updates the profile
count and an empty-directory message.} Within each card, a valid
\texttt{siteURL} links the handle to the published feed and the repository
URL is shown as a separate link. \texttt{style.css} controls the visual
layout. The website makes directory entries discoverable; the client's Follow validation—not the web page—checks that a handle, key and repository agree. Figure~\ref{fig:implementation_social_directory} shows an example of the rendered social-directory website.

\subsection{Replication}

Replication is triggered through the command: 
\begin{itemize} 
    \item \texttt{replicate} 
\end{itemize}
As described in the Following and Discovery section, following adds
the target repository as a named remote. Replication also processes the
configured canonical repository, which is cloned when an identity is
created. The workflow in Figure~\ref{fig:replication_workflow} is implemented
by \texttt{Replicator}: it requires the local repository to be on
\texttt{main}, skips the user's \texttt{origin}, and fetches the \texttt{main}
branch of each other remote. This branch check keeps replication from being
run on the published \texttt{gh-pages} branch. The fetched remote branch is
not merged wholesale; only accepted action JSON files are written into the
local \texttt{social/actions/} directory, keeping the local profile and
identity separate. \textbf{Listing~\ref{lst:replication-sources} shows the
branch guard and remote selection.}

\begin{lstlisting}[caption={Selecting replication sources and checking their profiles},label={lst:replication-sources}]
branch = self.repo.git.rev_parse("--abbrev-ref", "HEAD")
if branch != "main":
    return

for remote in self.repo.remotes:
    if remote.name == "origin":
        continue
    remote.fetch("main")
    self._verified_remote_public_key(remote.name)
\end{lstlisting}

\textbf{Git fetch makes the remote branch's objects available locally; it
does not decide which social actions to accept.} After fetching, the client
verifies the remote repository's
\texttt{social/profile.json} with \texttt{ProfileVerifier}. It then reads
candidate \texttt{.json} files from that remote's
\texttt{social/actions/} tree. Unreadable or malformed files are rejected;
each readable action is passed to \texttt{ActionVerifier} before being
written locally. The verifier checks the signature against the public key
contained in that action's \texttt{author} field. Profile verification and
action verification are separate checks: the former validates the remote
profile, while each action's signature is checked independently.
\textbf{Listing~\ref{lst:replication-verify} shows the action check before
local storage.}

\begin{lstlisting}[caption={Verifying candidate actions before local storage},label={lst:replication-verify}]
action = json.loads(raw_action)
if not ActionVerifier.verify(action):
    print(f"[REPLICATE] Rejected invalid action {action_file}")
    continue

local_path = os.path.join(self.identity_repo_root, action_file)
os.makedirs(os.path.dirname(local_path), exist_ok=True)
with open(local_path, "w", encoding="utf-8") as action_handle:
    json.dump(action, action_handle, indent=2)
\end{lstlisting}

\textbf{The client writes accepted files at the same relative path. Because
it verifies each action against the key in that action's \texttt{author}
field, a repository can relay another user's signed action without changing
its author or signature.}

\textbf{After a remote has been processed, the client stages
\texttt{social/actions/} and checks whether the repository is dirty. In
GitPython, the check compares the index with HEAD and the tracked working tree
with the index;
\texttt{untracked\_files=True} also includes untracked files. If replication
adds nothing and the repository is otherwise clean, the client skips the
commit. Listing~\ref{lst:replication-commit} shows this check and the commit
message. Errors verifying or reading a remote are reported and the loop
continues to the next configured remote. After processing the remotes, the
client attempts to push the updated local \texttt{main} branch to
\texttt{origin}.}

\begin{lstlisting}[caption={Staging and committing replicated actions},label={lst:replication-commit}]
self.repo.git.add("social/actions")
if self.repo.is_dirty(index=True, working_tree=True, untracked_files=True):
    self.repo.git.commit(
        "-m", f"Merge verified actions from {remote.name}/main"
    )
\end{lstlisting}

\textbf{“Merge” here is only text in the commit message; the code stages and
commits copied action files, without running \texttt{git merge}. The copy is
shown in Listing~\ref{lst:replication-verify}. This acceptance step enables
the multi-hop propagation in Figure~\ref{fig:multihop_replication}, with each
client verifying the original action signature.}



\subsection{Feed Construction and Site Publication}
Feed construction is accessed through: 
\begin{itemize} 
    \item \texttt{feed} 
    \item \texttt{publish-site} 
\end{itemize}
The previous section ends with verified actions available in the
local repository. The \texttt{publish-site} command, handled by
\texttt{SitePublisher}, packages this current local state as a static website;
it does not perform replication. This differs from the \texttt{feed} command,
handled by \texttt{ShowFeedAction}, which displays a feed in the terminal.
Figure~\ref{fig:feed_construction_workflow} in the System Design chapter
shows the overall workflow; this section focuses on how the prototype builds
and publishes the site.

\texttt{SitePublisher} first validates that the template contains
\texttt{index.html}, \texttt{app.js} and \texttt{style.css}. It verifies the
user's profile with \texttt{ProfileVerifier} and reads each local action as
JSON, using \texttt{ActionVerifier} to exclude unreadable or invalidly signed
actions from the generated feed. \textbf{Listing~\ref{lst:site-actions}
shows the signature check: invalid actions are skipped, while valid ones are
added to the list that will be serialized.}

\begin{lstlisting}[caption={Including only verified actions in the site feed},label={lst:site-actions}]
if not ActionVerifier.verify(action):
    continue
actions.append(action)
\end{lstlisting}

For readable author names, the publisher uses
\texttt{urllib.request} to retrieve profiles from repository URLs listed in
the public directory. Each retrieved profile is checked with
\texttt{ProfileVerifier}, and its signed handle and public key are compared
with the directory entry before a name is added to the mapping. Profiles
that cannot be retrieved or verified are omitted, allowing the frontend to
display the author's public key instead. This lookup supports feed
presentation and is separate from the Follow-time validation described
above. \textbf{Listing~\ref{lst:site-profile-names} shows how a discovered
profile is matched to the directory before its display name is accepted.}

\begin{lstlisting}[caption={Checking discovered profiles before adding display names},label={lst:site-profile-names}]
with urllib.request.urlopen(profile_url, timeout=5) as response:
    remote_profile_data = json.load(response)

remote_profile = ProfileVerifier(remote_profile_data).verify()
if remote_profile["handle"] != handle:
    raise ValueError("Directory handle does not match signed profile")
if remote_profile["publicKey"] != user_info.get("publicKey"):
    raise ValueError("Profile key does not match directory")
profiles.setdefault(
    remote_profile["publicKey"],
    remote_profile_data.get("displayName") or remote_profile["handle"],
)
\end{lstlisting}

The verified profile, profile-name mapping and action list are
assembled into a dictionary and written as the user's \texttt{feed.json}.
This is the data contract between the Python publisher and the browser
frontend: it contains the information needed to render the profile and
social actions, rather than the HTML page itself.
\textbf{Listing~\ref{lst:feed-data} shows this structure.}

\begin{lstlisting}[caption={Assembling the profile, names and verified actions for feed.json},label={lst:feed-data}]
profile = self._load_profile(profile_path)
return {
    "profile": profile,
    "profiles": self._load_profile_names(profile),
    "actions": self._load_verified_actions(),
}
\end{lstlisting}

The shared frontend is stored in the \texttt{site-template} directory
of the local \texttt{canonical-social} repository. 
The shared site template is organised as follows: \begin{verbatim} 
site-template/ 
├── index.html # Feed page structure 
├── app.js # Feed loading and rendering 
└── style.css # Site styling 
\end{verbatim}

The publisher copies these files into the \texttt{gh-pages} branch and generates a fresh \texttt{feed.json} containing the user's verified profile and actions.

The publisher uses \texttt{shutil.copytree()} for template subdirectories and
\texttt{shutil.copy2()} for individual files. It skips any template
\texttt{feed.json}, because the current profile, profile-name mapping and
verified actions are serialized to a fresh \texttt{feed.json} using
\texttt{json.dump()}. This keeps the shared presentation files separate
from feed data generated from the user's local protocol state.

The template's \texttt{index.html} defines the profile card and feed
section. Its element IDs—such as \texttt{profile-name},
\texttt{profile-handle}, \texttt{feed-status}, \texttt{post-list} and
\texttt{feed-filter}—provide the targets that \texttt{app.js} selects with
\texttt{document.querySelector()}. The filter defaults to showing all posts
including posts received through multi-hop replication, and can be changed
to show followed authors. \textbf{Listing~\ref{lst:feed-dom} shows how
JavaScript selects the page elements it updates.}

\begin{lstlisting}[caption={Connecting feed page elements to app.js},label={lst:feed-dom}]
const profileName = document.querySelector("#profile-name");
const feedStatus = document.querySelector("#feed-status");
const postList = document.querySelector("#post-list");
const feedFilter = document.querySelector("#feed-filter");
\end{lstlisting}

When the page loads, \texttt{loadFeed()} fetches the published
\texttt{feed.json} and passes the parsed object to \texttt{prepareFeed()}.
That function indexes posts by ID, likes and replies by their target, and
retains Follow actions for the filter. \textbf{Listing~\ref{lst:feed-index}
shows the post index; separate branches group likes and replies by their
targets and collect Follow actions for the filter.}

\begin{lstlisting}[caption={Indexing action types for feed rendering},label={lst:feed-index}]
if (action.type === "post") {
  postsById.set(action.id, action);
}
\end{lstlisting}

\texttt{loadFeed()} then passes this prepared data to the rendering
functions and updates the page elements selected above. In
\texttt{renderPost()}, the maps let the client display likes and replies
alongside the post they reference; \texttt{renderFeed()} uses Follow actions
to apply the selected author filter. The \texttt{feed-status} element reports
empty-feed or loading errors. \texttt{style.css} supplies the colours,
typography and layout for the rendered page, using the same visual style as
the social directory.

Before switching to \texttt{gh-pages}, the publisher checks for
uncommitted changes, a detached HEAD and a missing \texttt{origin} remote,
and refuses to proceed if these conditions make publication unsafe. The
detached-HEAD check is applied at the same stage.
\textbf{Listing~\ref{lst:site-guards} shows the checks made before fetching
the remote.}

\begin{lstlisting}[caption={Checking the repository before site publication},label={lst:site-guards}]
if self.repo.is_dirty(untracked_files=True):
    raise RuntimeError("Commit or remove local changes before publishing")
if self.repo.head.is_detached:
    raise RuntimeError("Cannot publish from detached HEAD")
if "origin" not in self.repo.remotes:
    raise RuntimeError("The user repository needs an origin remote")

origin = self.repo.remotes.origin
origin.fetch()
\end{lstlisting}

After fetching, the publisher prepares the site branch: an existing
local branch is checked out and fast-forwarded where possible; a remote-only
branch is checked out as a tracking branch; and if no site branch exists, an
orphan \texttt{gh-pages} branch is created and cleared. These Git operations
keep the static files separate from protocol data on \texttt{main}. After
copying the template and generating \texttt{feed.json}, the publisher stages
and commits changes, pushes \texttt{gh-pages} to \texttt{origin}, and returns
the working copy to its original branch.
\textbf{Listing~\ref{lst:site-branch} shows the three branch preparation
cases.}

\begin{lstlisting}[caption={Preparing the gh-pages branch for publication},label={lst:site-branch}]
if local_branch is not None:
    self.repo.git.checkout("gh-pages")
    if remote_ref is not None:
        self.repo.git.merge("--ff-only", remote_ref.path)
elif remote_ref is not None:
    local_branch = self.repo.create_head("gh-pages", remote_ref)
    local_branch.set_tracking_branch(remote_ref)
    self.repo.git.checkout("gh-pages")
else:
    self.repo.git.checkout("--orphan", "gh-pages")
    self.repo.git.rm("-r", "-f", ".")
\end{lstlisting}

After a successful push, \texttt{PublishManager} records the derived \texttt{siteURL} in the directory, provided the repository URL and public key match the registered entry. GitHub Pages serves the published files, so the website reflects the local protocol data available when \texttt{publish-site} runs. Later posts or replicated actions appear after the site is published again. Figure~\ref{fig:published_social_feed} shows an example of the resulting published feed website.

The tests use temporary data and controlled dependencies to make the checks
repeatable without changing the user's identity. Pytest's temporary
directories hold test profiles, actions and keys. PyNaCl performs signing and
verification with real test keys, so the cryptographic results are not
mocked. For directory and profile lookups, \texttt{monkeypatch} supplies
controlled HTTP responses, including missing or invalid data, without relying
on a live directory. Other tests use temporary Git repositories and bare
remotes to exercise real fetch, commit and push operations without publishing
to a hosted account. Profile-creation tests also clone the configured
canonical repository into a temporary project, so those tests still depend
on that repository being reachable.

This table describes the test approach and representative cases. The Results
chapter reports the observed end-to-end demonstrations, test outcomes and
coverage, and uses the table as context rather than repeating the test
inventory.

\subsection{Implementation Limitations}

Action identifiers use a sequential counter based on the action files
present in the local repository. If the same identity creates actions
concurrently from separate repository copies, those copies may select the
same next identifier.
