\subsection{Discussion} 
\subsubsection*{Identity and Portability} Discuss: 
\begin{itemize} 
\item Public-key identities. \item Host-independent identity. \item Separation of identity from repository location. \item Repository migration without identity loss. 
\end{itemize} 
Compare with: 
\begin{itemize} \item ActivityPub. \item Nostr. \item AT Protocol. 
\end{itemize} 
The implemented protocol did not bind identity to a single hosting provider as the protocol uses a public-key-based indentity model, where each user's identity is defined by the Ed25519 public key in the user's profile.json which is independently hosted across git repositories. Thus repository migration can happen without identity loss. Compared to earlier surveyed protocols we discussed like ActvityPub where identity was tied to servers, and it contrasted with Octotown who was dependent on GitHub only. The approach was more aligned with Nostr 
static profile file. The user's private key is responsible for signing social actions. Also, the protocol mirrors the basic principle shown in Social4Git where identity can move between Git providers. Although the public key is the authoritative identity, it is mapped to a human-readable handle in the profile file allowing the discovery layer to find users similar to the AT protocol which supplements portable identity systen with human-readable domain handles. However this brings trade-off as their must be trust in directory for handle-to-key verification.

\subsubsection*{Replication and Distribution} Discuss: \begin{itemize} \item Pull-based replication. \item Repository-centric distribution. \item Multi-hop replication. \item Trust remaining with the original author. \end{itemize} Compare with: \begin{itemize} \item ActivityPub federation. \item Nostr relay model. \item Secure Scuttlebutt replication. \end{itemize} 

The protocol made use of pull-based replication, where clients fetch only new social data since their last known state. Instead of having to store followed users in client side files and copying across files, existing git infrastructure is used. Git inherently supports incremental replication. 
In contrast to Git-as-Transport which transferred entire git history which was highlighted as replication bottleneck. ActivityPub showed that push fan-out (where updates are pushed to each follower) create load and scaling issues as push delivery becomes expensive as number of followers grow - reinforcing need for a pull-based model. Simiarly, Nostr replication although decentralised was shown to be insufficient due to unreliability of relays. The protocol mirrors the surveyed Git-based prototypes (Gitsocial, Social4Git, Gitweets) where posting = push, commit and replcication = fetch commits to only transfer new commits. However it is slightly different as only the social/actions files are replicated across, keeping social activity and identity (profile.json) separate. The protocol further supports an interesting property called Multi-Hop Propogation as users can recieve post from the users they don't follow by replicating although trust still remains with the original author of the post and not the follower the user got the social action through.

\subsubsection*{Discovery and Usability} Discuss: \begin{itemize} \item Human-readable handles. \item Directory-based discovery. \item GitHub Pages publication. \item Browser-based feed access. \end{itemize} \subsubsection*{Comparison with Existing Systems} Discuss: \begin{itemize} \item ActivityPub. \item Nostr. \item Secure Scuttlebutt. \item AT Protocol. \item Gitweets. \item Social4Git. \item GitSocial. \end{itemize} Discuss strengths and weaknesses relative to each. 

One of the key problems of the explored protocols was that did not support decentralised discovery mechanism where clients can locate user profiles and cotnent and content across different hosting providers without requiring central server.  ActivityPub introduces dicovery but is server-mediated via WebFinger making it unsuitable for static hosting. Whie AT Protocol uses a DID Service for a DNS-based global handle registry, which introduces centralisation. Nostr was less centralised with relay servers but is different approach to this protocol. The protocol aimed to address the problems of existing git based protocols like Gitweets and Socia4Git which require to know each other's repository URL to follow each other by mapping user handles to this URL in a dedicated social directory which is statically hosted. While this has own downside as may not be fully decentralised since need to trust owner of the reposiotry but still protocols itself doesn't couple to GitHub like Octotown which depends on GitHub's follows system. 

With respect to usability, the directory repository is hosted in github pages and automatically when user is created and published their profile is added to the directory and pushed so the static site gets update in short amount of time and gets rendered nicely. The user can then easily find people to follow marked by their human readable handle and the repository URL button takes them to their corresponding repository where thy can use the link to follow and interact with that user. This is much more usable compared to the primitive git-based models seen which are all terminal based and url is required to know. Furthermore user's can deploy their feed for the current state of their social/actions. This similarly is hosted on GitHub Pages on their gh-pages branch. It provides the user's own details in profile and all the posts in the user's feed with the author and content and time/date posted along with any likes and replies. Also a filter is provided to allow users to view only posts from users who are directly followed. 

Thus compared to existing git-based protocols the implemented static pages for rendering content is major improvement as none provide show a rich rendering experience for users to view their feed and find other users. But the core protocol actions still require utilising a command line interface and running commands like 'python app.py replicate' for respective functionality which will be discussed in limitations further. However this is still better than models like Gitweets which exposes git operations to users meaning they must understand native commands like git fetch. Thus the core functionality Command line is more similar to protocols social4git and gitsocial which abstract further with commands like social4git sync. Although the static site rendering shows usuability is improved from existing protocols but still needs work on in the future.

\subsubsection*{Static Hostable - provider agnostic/interoperability}
The protocol is not locked into a single provider compared to ActivityPub which showed the high infrastructure cost and centralisation drawback of server-based hosting. While Octotown reinforced danger of depending on single provider (GitHub). Git infrastructure has been seen to be reliable with many git-based prototypes using Git Hosting from established infrastructure while static hosting in sAT enables it to run fully on static files. Thus the protocol was a hybrid of this to define a standard format which any git-based social client can use across git-supported static host by reusing existing infrastructure.

\subsubsection*{Structured JSON Encoded Social Actions}
The protocol represents social actions (e.g. post, reply, follow, like) using a small, predefined set of action types which is building upon existing protocols like ActivityPub which showed how sturcutred social activites provide a rich social vocabularly and Nostr similarly used different type for different social actions. The encoded storage for these action types is JSON which the clients generate automatically when user perform social actions. This is similar to sAT and Git-as-Transport who store posts as JSON files reinforcing the flesibla extensible nature of JSON for social data and can support future extensions like media and references. This is an improvement on other Git-based protocols like Gitweets and GitSocial which showed limitations of embedding posts inside commit message and how it is unsuitable for structured posts.
